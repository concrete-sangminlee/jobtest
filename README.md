# HiBrain Job Alert

[hibrain.net](https://hibrain.net) 신규 채용공고를 Slack으로 알리는 GitHub Actions 봇.

하루 3회 예약되어 있다 (cron 09:07 / 14:07 / 19:07 KST). **GitHub의 예약 실행은 시각을
보장하지 않는다.** 이 저장소에서는 실제로 수 시간씩 늦게 시작하는 일이 흔하다.

```
수집 → 신규 선별 → 마감 임박 순 정렬 → 상세 보강 → 키워드 필터
     → 채널별 발송 대기열에 저장 → 채널마다 나눠 전송 (묶음마다 저장)
     → 마감 임박 리마인더 → 수집 상태 감시 (연속 실패 시 경보)
```

## 무엇을 보장하나

**조용히 죽지 않는다.** 공고 수집이 실패하면 실행이 실패(빨간색)로 끝나고, Actions
요약 맨 위에 원인이 한 줄로 나온다. 연속 2회 실패하면 Slack으로 경보를 보내고,
실패가 이어지는 동안에는 하루 한 번만 다시 알린다. 다시 성공하면 복구 알림을 한 번
보낸다. 웹훅 시크릿이 비어 있어도 사이트에 요청하기 전에 실패로 멈춘다.
스크립트가 스스로 보고하지 못한 실패(설치 실패, 시간 초과, 상태 푸시 실패)는
워크플로 마지막 단계가 Slack에 알린다.

**알림을 잃지 않는다.** 보낼 공고는 먼저 채널별 대기열(`outbox.json`)에 저장한 뒤
보낸다. 묶음 하나가 전달될 때마다 상태를 저장한다. 한 채널이 잠깐 죽어도 그 채널의
몫은 다음 실행에 이어서 나가고, 다른 채널에는 중복으로 가지 않는다. 사이트 수집이
실패한 날에도 밀린 알림과 리마인더는 나간다.

**쏟아지지 않는다.** 채널마다 한 실행에 메시지 `MAX_MESSAGES`개(기본 5개 × 20건)까지만
보낸다. 나머지는 다음 실행으로 넘어간다. 오래 밀린 항목(기본 3일)과 마감이 지난 공고는
대기열에서 정리한다. 새로 추가한 채널에는 지난 공고를 다시 보내지 않는다.

**잘못된 상태로 대량 재알림하지 않는다.** `seen_jobs.json`이 깨져 있으면 빈 목록으로
진행하는 대신 실행을 멈춘다. 그대로 진행하면 목록의 모든 공고가 '신규'가 된다.
상태 파일은 임시 파일에 쓴 뒤 교체하므로 중간에 죽어도 반쯤 쓴 파일이 남지 않고,
워크플로는 올바른 JSON이 아닌 상태 파일을 커밋하지 않는다.

전달은 "최소 한 번"이다. Slack이 메시지를 받은 직후 응답이 끊기면 그 묶음 하나가
다음 실행에 한 번 더 갈 수 있다. (Slack 웹훅에는 중복 방지 키가 없다.)

## 수집과 사이트 정책

목록 페이지 1회 요청으로 공고를 가져오고, 알릴 공고에 한해 상세 페이지의 schema.org
`JobPosting` 정보(기관명·기관유형·직종)를 덧붙인다. hibrain.net의 `robots.txt`는
일반 봇을 허용하지 않으므로 요청은 최소로 한다:

- 상세 보강은 실행당 최대 30건, 동시 3개. 첫 요청이 차단(401/403/429)되면 나머지는 보내지 않는다.
- 401/403처럼 다시 해도 같은 응답은 재시도하지 않는다.
- 상세 보강은 `ENRICH=false`로 끌 수 있다. 그러면 사이트 요청은 실행당 목록 1회뿐이다.

**현재 알려진 상태 (2026-11):** 사이트가 GitHub Actions 러너의 접속을 403으로 거부하고,
`SCRAPER_API_KEY`는 401(키 무효)로 거부된다. 이 상태에서는 실행마다 수집 실패 경보가
나간다. 복구하려면 아래 중 하나가 필요하다.

1. ScraperAPI 키를 새로 발급해 `SCRAPER_API_KEY` 시크릿을 갱신한다.
2. 하이브레인(help@hibrain.net)에 공식 알림 채널이나 자동 수집 허용을 문의한다.
3. 하이브레인 회원 기능(맞춤정보·관심기관)에 메일 알림이 있다면, 그 메일을 Slack 채널 이메일 주소로 전달한다. (기능 유무는 확인하지 못했다)

## 설정

### 시크릿

| 이름 | 필수 | 설명 |
| --- | --- | --- |
| `SLACK_WEBHOOK_URL` | ✅ | Slack Incoming Webhook URL. 콤마로 여러 개를 넣으면 모든 채널에 보낸다. 같은 주소는 한 번만 보낸다. |
| `SLACK_ALERT_WEBHOOK_URL` | | 봇 상태 경보(수집 실패·복구)를 받을 별도 채널. 없으면 공고 채널로 보낸다. |
| `SCRAPER_API_KEY` | | ScraperAPI 키. 있으면 목록을 먼저 이 경로로 가져온다. |

웹훅 토큰은 로그에 찍히지 않는다. 채널은 `채널 1 (.../B0A.../***)`처럼 표시된다.
여러 URL을 콤마로 합치면 GitHub의 시크릿 마스킹이 개별 URL에는 걸리지 않기 때문에
코드에서 직접 가린다. 저장소에 커밋되는 상태 파일에도 웹훅 주소는 들어가지 않는다.

### 저장소 Variables (모두 선택)

`Settings → Secrets and variables → Actions → Variables`에서 코드 수정 없이 조절한다.

| 이름 | 기본값 | 설명 |
| --- | --- | --- |
| `REMINDER_DAYS` | (없음) | 마감 임박 리마인더 기준. 예: `3,1`. 비우면 꺼짐. |
| `JOB_INCLUDE_KEYWORDS` | (없음) | 이 키워드 중 하나라도 들어간 공고만 알림. 제목·기관명·기관유형·직종을 대소문자 무시하고 검사. |
| `JOB_EXCLUDE_KEYWORDS` | (없음) | 이 키워드가 들어간 공고는 제외. include보다 우선한다. |
| `JOBS_PER_MESSAGE` | `20` | 한 메시지의 공고 수. Slack 블록 제한 때문에 44를 넘기면 44로 조인다. |
| `MAX_MESSAGES` | `5` | 채널마다 한 실행에 보낼 최대 메시지 수. |
| `ENRICH` | `true` | `false`면 상세 보강을 하지 않는다. |

환경변수로만 조절하는 값: `FETCH_MAX_ATTEMPTS`, `FETCH_BACKOFF_BASE`, `SCRAPERAPI_TIMEOUT`,
`DIRECT_TIMEOUT`, `SLACK_TIMEOUT`, `SLACK_MAX_ATTEMPTS`, `ENRICH_WORKERS`, `ENRICH_TIMEOUT`,
`ENRICH_MAX`, `OUTBOX_TTL_DAYS`, `OUTBOX_MAX_PENDING`, `HEALTH_ALERT_AFTER`,
`HEALTH_REALERT_HOURS`, `TRACK_LIMIT`.

### 마감 임박 리마인더

`REMINDER_DAYS`를 채우면 켜진다. 알린 공고를 `tracked_jobs.json`에 기록해 두고,
기준일이 되면 별도 메시지(주황색)로 한 번 더 알린다. 지나간 기준은 한 번에 모두
소비하므로 같은 공고가 이틀 연속 리마인더로 나가지 않는다. 신규 알림 시점에 이미 지난
기준도 소비 처리해, D-2 공고가 같은 실행에 신규+리마인더로 두 번 나가지 않는다.
리마인더는 사이트 요청이 필요 없어서 수집이 실패한 날에도 나간다.

## 수동 실행

Actions → `Check hibrain.net Job Postings` → `Run workflow`에서 `mode`를 고른다.

| mode | 동작 |
| --- | --- |
| `dry-run` (기본) | 목록을 가져와 보낼 메시지만 만들어 본다. 전송·상태 변경·상세 요청 없음. 웹훅은 아예 넘기지 않는다. |
| `test-message` | 샘플 공고로 실제 메시지를 한 번 보낸다. 상태는 바꾸지 않는다. |
| `live` | 예약 실행과 같다. |

Slack으로 나가는 수동 실행(`test-message`, `live`)은 기본 브랜치에서만 허용된다.

## 로컬 실행

```bash
pip install -r requirements-dev.txt

python scraper.py --mode dry-run           # 보내지 않고 미리보기
python -m pytest tests/ -v                 # 테스트 (네트워크 사용 안 함)
```

`--mode live`(기본값)는 `SLACK_WEBHOOK_URL`이 없으면 실패로 끝난다.

## 종료 코드

| 코드 | 의미 |
| --- | --- |
| 0 | 정상 (새 공고가 없어도 0) |
| 1 | 무언가 실패: 수집 실패, 웹훅 없음, 채널 전송 실패, Slack이 메시지 거부, 상태 파일 문제 |
| 2 | 잘못된 실행 인자 |

## 상태 파일

모두 워크플로가 실행 후 커밋한다. 공개 저장소이므로 공개된 공고 정보만 담는다.

| 파일 | 내용 |
| --- | --- |
| `seen_jobs.json` | 더 찾을 필요가 없는 공고 ID 목록 (전달됨·필터 제외·포기). 최근 2000건. 이전 버전 코드와 형식이 같다. |
| `outbox.json` | 채널별 미전송 대기열. 채널은 웹훅 주소 해시의 앞부분으로만 구분한다. |
| `health.json` | 수집 연속 실패 횟수, 실패 시작 시각, 마지막 경보·성공 시각. |
| `tracked_jobs.json` | 리마인더 추적 상태. `REMINDER_DAYS`를 쓸 때만 생긴다. |

복구가 필요하면 각 실행의 artifact(`job-alert-<run>`, 14일 보관)에 상태 파일 사본이 있다.
`seen_jobs.json`이 손상되어 실행이 멈췄다면 이전 커밋의 파일로 되돌리면 된다.

## 저장소 활동 유지

공개 저장소의 예약 워크플로는 60일 동안 저장소 활동이 없으면 GitHub이 끈다.
`keepalive.yml`이 매월 1일·15일에 GitHub API로 예약 워크플로를 다시 켠다. 수집이
실패하는 동안에도 `health.json`이 매 실행 커밋되므로 저장소 활동은 계속 생긴다.
